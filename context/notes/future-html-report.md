# Future feature — HTML session report

> Captured 2026-05-20 alongside the LiteDB migration discussion. Not for now;
> stored so the idea survives chat compaction.

## The idea

LiteDB is the storage layer (not human-readable, never meant to be read by
humans directly). For users who want to *see* their session data, we ship
a separate "generate HTML report" tool that:

1. Reads from the LiteDB file
2. Templates the data into a self-contained HTML file (CSS + JS embedded)
3. Looks similar to `design/Mockups.html` — the visual mockup we already have
4. Saves to a known location (probably alongside the LiteDB file or in a
   `reports/` subdir)

The user double-clicks the HTML; it opens in their browser; they see their
playthrough's performance story visually. No game required, no profiler
overlay, no terminal.

## When the HTML gets generated

Three plausible triggers (pick the one that fits when this lands):

- **On world save & quit** — auto-generates the latest session's report
  every time the player exits. "Did I have a bad session? Let me open the
  HTML and see."
- **On demand via an in-game command or menu button** — `/profiler-report`
  or a button in the overlay. User chooses when to generate.
- **Both** — auto on exit (cheap, no-op if data hasn't changed) and on
  demand whenever the player wants.

I lean towards "both" but defaulting to on-exit. Cheap to write a few KB of
HTML at session end; no friction for the player.

## What the report should contain

Mirrors the eventual six views from the README:

1. **Session header**: world name, modlist fingerprint + named mods,
   duration, total ticks, avg / median / p99 frame ms, GC pause summary.
2. **Mod ranking** (the aggregated overview tab in HTML form): every mod
   sorted by composite impact with CPU / MEM / spike contribution bars.
3. **Mod detail cards**: per-mod card with categories breakdown, top hooks,
   spike participation, allocation patterns. The "design.html mockup" view.
4. **Encounter / events timeline**: visual timeline of biomes entered,
   bosses fought, blood moon windows, with the per-bucket performance
   stats from the events tab.
5. **Spike feed**: every spike during the session with worst tick, baseline,
   top contributors, context summary.
6. **Insights**: rendered InsightRecords from the engine (M4+).

Plus a "compare to previous sessions" pane when there's more than one
session in the LiteDB (M4+ retrospective territory).

## Technical shape

- **One self-contained HTML file** — embedded CSS, embedded JS, embedded
  fonts if any. The user can email/Discord-paste this file and a recipient
  sees the same thing. No network requests when opened.
- **Charts via Chart.js or D3** — embedded as a `<script>` block, no CDN
  reference. Use plain JS and `<canvas>` rendering; keep it small.
- **No build step at user time** — we ship a Mustache-style template + a
  data-injection function; the .tmod's report-generator method picks up the
  current session from LiteDB, fills the slots, writes the file.
- **Where the template lives** — embedded as a string resource in the mod
  assembly, or shipped as a `report-template.html` next to the .tmod.
  Embedded is simpler.
- **Size budget** — a generated HTML for one session should be < 1 MB
  even for a 12-hour Calamity playthrough. Charts use aggregated data,
  not raw per-tick.

## Why this matters

- **Shareability** — "here's my profile, can someone explain why I'm
  lagging?" becomes one attachment in Discord. No "send me your logs and
  also screenshots and also describe your modlist" back-and-forth.
- **Persistence** — the HTML survives mod uninstalls, tModLoader updates,
  whatever. A snapshot of "what my game was doing on May 20".
- **Comparison** — open two reports side-by-side in different browser
  tabs. Visual diff. No tooling needed.
- **Modder feedback** — a mod author can be sent a report and immediately
  see "your hook is 54% of this player's mod cost", without needing the
  player's exact modlist or a debug build of the profiler.

## What's NOT this feature

- Not a live web dashboard.
- Not a server upload.
- Not a community leaderboard.
- Not a comparison-to-other-users feature.

Local file, generated by the mod, opened by the user when they want it.
The privacy story is "the file is on your disk, nothing leaves your
machine unless you share it."

## Dependency cost

- No new runtime dependencies in the mod (HTML generation is just string
  templating).
- Embedded chart library (~50–100 KB minified) lives in the template.
- Plain string concatenation or a tiny template engine is enough; no need
  for Razor / RazorLight / etc.

## When this lands

Bundle with M4 (Insights Engine) or M5 (Workshop Release). It's a polish
feature, not core. The LiteDB schema needs to be settled first so the
template's data-injection points are stable.

For now: not implemented. The LiteDB migration is the foundation that
makes this possible.
